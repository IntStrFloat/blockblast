# Android game audio verification

The Android implementation now uses the local `GameAudio` Expo module and
Android SoundPool. Ten short WAV samples are decoded before use. Each call
starts an independent native stream; pickup/drop no longer wait for a media
player's finish notification or asynchronous rewind. The existing Expo player
implementation remains in use on the other platforms.

Assets are copied from `assets/sounds` by the module's Gradle task. A native
rebuild is required. The debug APK was compiled and installed on Android 17 /
API 37, x86_64 (16 KB page-size image).

## Automated checks

- Debug Android build: successful.
- TypeScript: successful.
- Full Jest run: 173 suites, 1108 tests passed.
- Android audio adapter tests cover rapid repeated dispatch, preload gating,
  release/reinitialize ordering, and retry after failed sample loading.
- Native review checked sample readiness, synchronization, old-pool callbacks,
  background stopping, and generated asset packaging. A sticky native load
  error found during review was addressed by releasing the failed pool before
  the next initialization attempt; the adapter regression test passed again.

## Runtime evidence

Method: record the emulator's video **and audio output** using the emulator
console, decode its Vorbis track to mono PCM WAV, and identify audible cues.
Compare with `GameAudio` Logcat events (name, stream ID, foreground state).
Native acceptance alone is not considered proof of audible playback.

Short taps can overlap pickup and drop. For these, analyze the separate
650–1600 Hz and 120–550 Hz bands, not just the number of contiguous non-silent
segments. Small system button clicks are distinct from the game cues.

Initial checks on emulator-5554:

| Scenario | Captured result |
| --- | --- |
| Three grab/return gestures | 3 pickups + 3 drops |
| Thirty rapid grab/return gestures | 30 pickups + 30 drops |
| Ten short taps without activated dragging | 10 pickups + 10 drops, including overlapping cues |
| Accepted placement | Pickup + drop; board and score updated |
| Placement clearing two lines | Pickup + complete clear2 cue; board cleared and tray refilled |
| Return from background, two gestures | 2 pickups + 2 drops; no stale replay |
| Sound setting off, then on | No game cues while off; 2 pickups + 2 drops after enabling |

The original emulator was shared with another task. One recording had an
unexpected background transition and incomplete audio; it was discarded.
Final checks use a separate emulator instance, emulator-5556, with the
`Tetris_Pixel_8` AVD, its own app installation, and Metro on port 8084.
The original emulator is not used for these final checks.

The second emulator uses media volume 5/15, so its PCM cues are quieter. The
band detector threshold is calibrated to 30 PCM units (versus 600 at the first
emulator's 15/15 volume). Native counts are independently compared. Boot-time
UI clicks and densely overlapping events in the first long recording are not
used as the pass/fail evidence; the clean recordings below are.

| Isolated scenario | Captured result |
| --- | --- |
| Classic, three grab/return gestures | 3 pickups + 3 drops (`isolated-recheck`) |
| Adventure, ten returns followed by an accepted placement | 11 pickups + 11 drops; objective score changed from 0 to 6 (`isolated-adventure`) |
| Five occupied drops, five short taps, background/foreground, two returns | 12 pickups + 12 drops; rejected placements did not change the board or objective (`isolated-edge-cases`) |

The isolated recordings contain all **52 expected game cues**, with no extra
game cues and no missing pickup/drop bands. Combined with the clean initial
checks above, **150 expected game cues** were verified in captured output.
The application is left running on emulator-5556 for manual follow-up.

Local recordings, decoded WAVs, native logs, and analysis scripts are stored
under `.omx/` (`sound-stress`, `sound-taps`, `sound-placement`, `sound-clear`,
`sound-resume`, `sound-toggle`). These diagnostics are not bundled into the app.
